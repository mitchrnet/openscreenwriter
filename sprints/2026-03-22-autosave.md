## Revision 2 — 2026-03-23

Four additional changes requested by Mitch after initial testing.

### 1. Debounced autosave (2s after last keystroke)

**Old behaviour:** A `setInterval` fired every 60 seconds.

**New behaviour:** The controller exposes `notifyChange()`. The editor calls it on every `tr.docChanged` transaction (WYSIWYG mode) and on every `input` event (source mode). A 2-second `setTimeout` is reset on each call, so a write fires 2 seconds after the user stops typing. If the user is actively typing, no intermediate writes occur. `setEnabled(false)` now also cancels any in-flight debounce timer.

**Files changed:** `renderer/editor/autosave.js` (replaced interval with debounce; added `notifyChange()`), `renderer/editor/index.js` (call `autosave.notifyChange()` from `dispatchTransaction` and `sourceEditor` input handler).

### 2. Autosave toggle button in toolbar

A small `AS` button now appears in the toolbar to the left of the theme toggle (☀/🌙). It shows as `.active` (highlighted) when autosave is on, and dimmed when off. Clicking it calls `autosave.setEnabled(toggle)`. The View menu checkbox remains as a keyboard-friendly alternative; both controls read/write the same `localStorage` key.

**Files changed:** `renderer/index.html` (added `#btn-autosave-toggle`), `renderer/editor/index.js` (wired click handler + `updateAutosaveToggleBtn()`).

### 3. macOS File menu

On macOS, Electron's first menu item is the system app menu. Previously the template started with `File`, which was treated as the app menu label on macOS — hiding Open/Save/Export under the app name instead of a proper `File` menu.

**Fix:** `buildMenu()` now checks `process.platform === 'darwin'` and conditionally prepends an `app.name` menu entry (About, Services, Hide, Quit). The `File` menu appears correctly as the second item on macOS and as the first item on Windows/Linux. Quit is only in the File menu on Windows; About is only in the Help menu on Windows (on macOS it's in the app menu).

**Files changed:** `main.js` (`buildMenu()` updated).

**electron-builder config:** Added `fileAssociations` (`ext: fountain`, `role: Editor`) and `appId`/`productName`/`mac`/`win` to the `build` key in `package.json`. After installing the next release, the OS can associate `.fountain` files with OpenScreenwriter.

**Launch handling:** Added `app.on('open-file')` for macOS (fires when a `.fountain` file is double-clicked in Finder) and `getArgFilePath()` for Windows (reads `process.argv`). Both send `menu:openPath` to the renderer once the window is ready. Added `file:readPath` IPC handler (reads a file by absolute path without showing a dialog). Exposed `readFileByPath` and `onMenuOpenPath` in `preload.js`. `openFile()` in the renderer now accepts an optional pre-loaded result so it can handle both dialog-opened and path-opened files without code duplication.

**Files changed:** `main.js`, `preload.js`, `renderer/editor/index.js`, `package.json`.

## Revision — 2026-03-22

Two issues were found and addressed after the initial implementation.

### Problem 1: Manual save produced empty files

**Root cause:** The `onManualSave` function in `autosave.js` had an inverted guard condition (`if (!savedFilePath)`) that attempted to delete the untitled recovery file even when saving a named file, and never cleaned it up on a first-ever save (untitled → named). More importantly, the signature did not distinguish between the *previous* path and the *new* path, so cleanup logic could not make the right decision. This caused the untitled recovery file to persist incorrectly, and in edge cases where the autosave tick fired concurrently with a save dialog, content state could be misread.

**Fix:** `onManualSave` now accepts a second argument `previousPath`. The untitled recovery file is only deleted when `previousPath` is null (i.e. the document was untitled before this save). `saveFile()` and `saveFileAs()` in `index.js` capture `currentFilePath` before the `await` and pass it as `previousPath`.

### Problem 2: Autosave redesigned to write to the real file

The original implementation wrote all autosaves to a hidden recovery location in `userData/autosave/`, requiring a confirmation dialog on next open. Mitch requested that autosave work like most modern writing apps: periodically overwrite the real `.fountain` file on disk.

**What changed:**

- **Named documents:** Every 60 seconds, if content has changed, autosave writes directly to the real `.fountain` file via a new `autosave:writeRealFile` IPC handler. No recovery file is created. If the app crashes, the user simply reopens the file — the last autosave IS the file.
- **Untitled documents:** The previous recovery-file behavior is retained as a fallback. If the app crashes before the user saves for the first time, the untitled recovery file is offered on next launch.
- **Recovery dialog for named files removed.** `checkRecovery()` immediately returns `null` for any non-null file path.
- **Autosave toggle added** to the View menu (checkbox item). The preference is persisted in `localStorage` under `autosaveEnabled` and read on every tick. Defaults to enabled.
- **`cleanQuit()` simplified** — no longer needs a file path argument. It only ever cleans up the untitled recovery file; named files are already correct on disk.

## What Was Built

Autosave support for OpenScreenwriter. Every 60 seconds, if the document content has changed since the last autosave, the current fountain text is written to a recovery file in Electron's `userData/autosave/` directory. On startup (or file open), if a recovery file exists for the relevant path, the user is offered a dialog to restore it. On a clean manual save or app quit, the autosave file is deleted so no stale recovery is offered next time.

Key behaviours:
- **60-second interval**, only fires when content has changed (SHA-free string comparison).
- **Recovery is path-specific**: file paths are SHA-1 hashed to produce a stable, filesystem-safe filename. Untitled documents use the key `untitled`.
- **Non-destructive**: autosave never touches the user's actual `.fountain` file.
- **Subtle status bar indicator**: the `#status-autosave` span flashes "Autosaved" for 2 seconds then fades out via CSS opacity transition.
- **Clean quit**: `beforeunload` sends a fire-and-forget IPC message to delete the autosave, so a normal close leaves no stale recovery file.

## Decisions Made Autonomously

1. **SHA-1 for path encoding** — simplest collision-resistant approach for turning an arbitrary file path into a filesystem-safe filename. SHA-1 is fine here; this is not a security context.

2. **JSON sidecar files** — each autosave blob gets a companion `.fountain.json` that records the original path. This lets `autosave:listAll` return human-readable metadata without parsing the fountain content.

3. **`window.confirm()` for recovery dialog** — the spec said "a simple dialog on startup is fine". Using the native browser confirm keeps the implementation minimal and avoids building a custom modal.

4. **Inline controller mirror in tests** — the autosave module depends on `window.screenwriterAPI` (Electron's contextBridge). Rather than mocking the entire Electron environment in Vitest (which runs in Node), the test file inlines an exact copy of the controller logic with an injected `api` parameter. This is slightly more code but keeps tests fast, hermetic, and honest about what they're actually testing.

5. **`beforeunload` for clean quit** — Electron fires `beforeunload` on window close even on macOS, so this is the most reliable place to send the cleanup signal without wiring up a custom close-prevention flow.

6. **`autosave:cleanQuit` as a one-way `ipcMain.on`** — it's fire-and-forget (renderer is about to unload) so `invoke`/`handle` isn't appropriate here; `send`/`on` is the right pattern.

7. **Deferred startup recovery check (500 ms timeout)** — the untitled-recovery check runs after `init()`, deferred so the startup modal is already visible. If the startup modal is still displayed the check is skipped entirely; recovery for untitled files is only offered after the user dismisses the modal and begins editing.

## What Mitch Should Verify Manually

1. **The 60-second cycle fires correctly** — open the app, type something, wait 60 seconds, confirm "Autosaved" appears briefly in the status bar bottom-center.

2. **Recovery dialog appears after a crash** — type some text, then force-quit the app (not a clean quit), relaunch, confirm a dialog offers to restore the document, accept it, and verify the content is restored.

3. **Recovery dialog does NOT appear after a clean quit** — save the file, quit normally (`Cmd+Q`), relaunch. No recovery dialog should appear.

4. **Named-file recovery** — open a `.fountain` file, make changes, wait 60 seconds (or force-quit), relaunch and reopen the same file. Confirm recovery is offered for that specific file only.

5. **Declining recovery** — when offered a recovery, click Cancel. Confirm the editor opens the saved-on-disk version, and that reopening the file again does NOT re-offer recovery (the autosave file should have been deleted on decline).

6. **Indicator appearance** — "Autosaved" should appear subtly in the status bar between the filename and page count. It should fade out after ~2 seconds. Confirm it is visible in both dark and light themes.

7. **No autosave offered after Save As** — after using Save As, confirm that subsequent relaunches do not offer recovery for the old path or the new path (assuming no further edits).
